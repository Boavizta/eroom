3. Demarche exploratoire
[statut : non valide]

Piste 1 : Sondes automatisees
  "Remplacer le jugement humain par du code deterministe"

  15 sondes (HAR, Coverage, Lighthouse, PageSpeed/CrUX, API ipinfo.io, SimilarWeb, CSP (Content-Security-Policy), .well-known...)
          |
          +----------------+------------------------
          |                                        |
          v                                        v
  mapping critere <-> sonde              modele e-footprint (Boavizta)
  (code interne au projet)               + EcoLogits pour l'IA generative tierce
          |                                        |
          v                                        v
  referentiel EOF                        estimation CO2e du parcours
  70 criteres, rempli auto               (chaque hypothese tracee :
  quand une sonde repond                  valeur / source / confiance)

Détails :
- HAR (capture DevTools) -> trafic reseau : requetes, domaines, volumes, codes HTTP
- Coverage Chrome DevTools -> code mort JS/CSS
- EcoIndex (formule officielle cnumr, calculee depuis le HAR) -> score 0-100 + grade A-G
- PageSpeed Insights / CrUX -> Core Web Vitals terrain (donnees reelles P75)
- Lighthouse (local) -> Core Web Vitals en labo, secours si pas de donnees terrain
- HAR, pattern-matching maison -> stack technique detectee
- En-tetes HTTP du HAR -> score de securite (type securityheaders.com)
- CSP (Content-Security-Policy : liste des domaines tiers, trackers, partie statique, mutualisation d'infrastructure, elasticite des plateformes) -> inventaire des tiers declares (plus large que ce que le parcours capture)
- API ipinfo.io (pays, fournisseur cloud, ASN, ...) + CrUX -> donnees d'environnement pour e-footprint (pays/hebergeur, mix d'appareils)
- SimilarWeb (API interne extension) -> trafic annuel + mix pays
- Fichiers publics standards (/.well-known, sitemap) -> requete HTTP directe
- HAR, parametres de version des assets -> fraicheur/atomicite de deploiement
- Pages HTML archivees -> declarations publiques d'impact environnemental
- HTML/CSS statique archive -> criteres EOF deterministes (autoplay, images adaptatives, media queries, viewport...)
- HAR -> detection d'appel a une IA generative tierce texte

Piste 2 : Moins de questions, autant de criteres
  "Les questions qui rapportent le plus de criteres, en priorite"
- Point de depart : questionnaire EOF a 62 questions pour 70 criteres
- Priorisation : les questions qui rapportent le plus de criteres sont posees en premier
- Diagnostic rapide + dimension 6 etudies a part : ratio deja proche du plancher, marge de reduction limitee
- Piege identifie : la reponse "A evaluer" compte comme repondue (gonfle la completude) sans apporter de score
- Filtre "hors perimetre" : ecarte d'un coup les criteres non applicables

Piste 3 : e-footprint, estimer le CO2e
  "Une estimation carbone sereine, mais mono-critere"
- Reutilise les donnees deja capturees (HAR, mix d'appareils CrUX, pays/hebergeur via ipinfo.io, trafic annuel SimilarWeb)
- Modele construit avec la bibliotheque e-footprint (Boavizta) ; le calcul d'une IA generative tierce est delegue a EcoLogits
- Chaque hypothese residuelle (duree de vie materiel, intensite carbone...) est tracee : valeur, source, confiance
- Limite assumee : demarche mono-critere (uniquement carbone), a l'oppose du principe multi-critere d'EROOM
- Ajout recent : gain CO2e/EcoIndex/LCP calcule par palier de recommandations (prio1, prio1+2, prio1+2+3)

Piste 4 : Rejouable et deterministe
  "Meme parcours capture, meme resultat, hors ligne"
- Archive du HTML/CSS retelecharge : l'audit redevient rejouable hors ligne, sans reseau
- Generation du questionnaire et du rapport rendue deterministe (memes entrees = meme sortie)
- Objectif : qu'un audit fait par une personne ou par un agent converge vers le meme resultat

Piste 5 : Capture reelle via Chrome DevTools
  "HAR + Coverage, un parcours humain non simule"
- Capture HAR (trafic reseau) + fichiers de couverture JS/CSS directement depuis Chrome DevTools
- Parcours realise a la main, en conditions reelles (non simule) : evite les surprises d'une saisie automatisee (Playwright ou autre)
- Consigne de capture : accepter les cookies avant de mesurer, sinon la mesure n'est qu'un plancher

4. Avantages, avec exemples
[statut : non valide]
- Gain de temps sur des taches repetitives et volumineuses (lecture de HAR, croisement de criteres)
- Exemple 1 : diagnostic rapide EOF, questionnaire de 62 questions couvrant 70 criteres, genere et exploite par l'agent
- Exemple 2 : calcul du gain CO2e/EcoIndex/LCP par palier de recommandations (prio1, prio1+2, prio1+2+3), produit et documente automatiquement
- Exemple 3 : diagrammes de composants et diagrammes d'architecture regeneres a la demande, coherents avec le code reel
- Un humain reste decisionnaire : l'agent structure et chiffre, la priorisation finale reste humaine

--

5. Limites
[statut : non valide]
- Difficulte de reduire le nombre de questions du questionnaire EOF sans perdre en precision (chaque question capte des criteres distincts, peu de redondance a retirer sans perte)
- Risque de boite noire : un chiffre ou un score produit sans que la source et le niveau de confiance de chaque hypothese soient visibles n'est pas exploitable tel quel
- Necessite de discipline methodologique : tracer systematiquement valeur/source/confiance en annexe, sinon le risque de boite noire revient
- Le diagnostic reste largement declaratif ou base sur des mesures externes (HAR, API tierces) : pas encore de branchement direct sur le code source de l'application auditee
